# Wire 1.5 契约与迁移

## 1. 文档地位与版本边界

本文是 VCPMobile 当前同步线协议的权威入口。旧文档仍可用于理解双通道、分阶段同步、清单比对和双哈希架构；涉及版本握手、阶段 ACK、Message/Topic 线上字段和错误语义时，以本文、Wire fixture 与运行时代码为准。

当前兼容边界如下：

| 项目 | 当前值 | 兼容性含义 |
|------|--------|------------|
| Wire | `1.5` | 唯一参与双端兼容仲裁的版本 |
| 桌面插件包 | `VCPMobileSync 2.0.0` | 仅作为诊断信息展示，不参与 Wire 仲裁 |
| 桌面后端 | `cds` 或 `legacy` | 握手后展示实际数据后端；不是协议版本 |
| Wire 1.4 | 不支持 | 不提供双栈或降级；不匹配时关闭会话 |

Wire 1.5 的上游起始提交是 `4ac525deb6baf672aa6a1b080a220fa24b1d30fe`。完整契约还包含此后补齐的结构化握手、最终 ACK、canonical Message 和 Topic 配置版本语义，因此不能只移植该单个提交。

桌面契约以当前 `VCPMobileSync` 插件实现及其 fixture 为唯一真实来源。移动端对应的五份镜像 fixture 位于 `src-tauri/src/vcp_modules/sync/fixtures/`：

- `version_handshake_contract.json`
- `wire_error_contract.json`
- `message_canonical_contract.json`
- `message_diff_matrix.json`
- `topic_canonical_contract.json`

## 2. 结构化版本握手

移动端建立 WebSocket 后发送：

```json
{
  "type": "VERSION_CHECK",
  "versions": [
    { "component": "mobile_app", "version": "<应用版本>" },
    { "component": "wire", "version": "1.5" }
  ]
}
```

桌面端接受后返回：

```json
{
  "type": "VERSION_ACK",
  "versions": [
    { "component": "desktop_plugin", "version": "2.0.0" },
    { "component": "wire", "version": "1.5" }
  ],
  "backendMode": "cds"
}
```

握手采用 fail-closed 校验：

- `versions` 必须精确包含两个声明，顺序不影响结果，但组件不得重复。
- `VERSION_CHECK` 只允许 `mobile_app` 与 `wire`；`VERSION_ACK` 只允许 `desktop_plugin` 与 `wire`。
- 版本 token 长度为 1–64 字节，首字节必须是 ASCII 字母或数字，其余字符只允许 ASCII 字母、数字、`.`、`_`、`+`、`-`。
- JSON 重复 key、尾随 JSON、未知字段、缺失或额外组件、非法字段类型均拒绝。
- `backendMode` 只接受 `cds` 或 `legacy`。
- Wire 值不是 `1.5` 时返回 `WIRE_VERSION_MISMATCH`；插件包版本不同本身不导致拒绝。

握手通过后，移动端把 `packageVersion` 与 `backendMode` 放入当前 session/attempt 的 open 事件。前端仅从该事件建立桌面信息，并在切换连接档、重试、停止、关闭或进入新会话时清理，防止展示上一会话的信息。

## 3. 阶段与最终 ACK

Wire 1.5 不使用普通阶段 ACK 作为流水线 barrier。`PHASE_START` 与 owner/topic 的 `PHASE_COMPLETED` 是单向阶段通知；移动端收到没有待确认最终帧的 `PHASE_ACK` 时按协议错误终止。

Messages 阶段遵循以下规则：

1. `changed_topics` 为空时不发送 messages 的 `PHASE_START`，直接执行本地 finalization。
2. 存在变化时发送 `PHASE_START { phase: "messages" }`，随后执行差异和传输，不等待普通 `PHASE_ACK`。
3. 本地 finalization 完成后，移动端先原子登记待确认身份，再发送唯一最终帧：

```json
{
  "type": "PHASE_COMPLETED",
  "phase": "messages",
  "sessionId": 11,
  "attemptId": 4,
  "nonce": "<本次随机值>"
}
```

4. 桌面端必须用字段完全相同、仅把 `type` 改为 `PHASE_ACK` 的五字段对象确认。
5. phase、sessionId、attemptId、nonce 任一不匹配，存在未知字段，重复确认，或当前没有 pending final ACK，均返回 `FINAL_ACK_INVALID`。超时返回 `FINAL_ACK_TIMEOUT`。

这个约束将最终确认绑定到一次具体 session/attempt，可阻止旧连接或并发重试的迟到 ACK 完成新会话。

## 4. Message canonical 契约

双向传输统一使用 `MessageSyncDTO`。核心约束如下：

- `contentHash` 必填，必须是 64 个小写十六进制字符表示的 SHA-256。
- `timestamp` 与 `updatedAt` 必须是 JavaScript 安全整数范围内的非负时间值。
- `name`、`agentId`、`groupId`、`topicId`、`isGroupMessage`、`finishReason` 与 `attachments` 为空时省略，不发送 `null`。
- `isThinking`、`avatarColor`、渲染 blocks、附件本地路径/状态和 tombstone 记账字段是本地状态，不得跨 Wire 传输；未知字段直接拒绝。
- 拉取时保存远端 `contentHash`；推送时数据库中缺失或非法的 `content_hash` 会阻止发送，不能现场用不同规则猜算。
- 附件只传 canonical 元数据与有效 SHA-256；本地 `src`、`internalPath` 等路径不得越过协议边界。

消息 canonical 字节和哈希行为由 `message_canonical_contract.json` 固定，涉及 Unicode key 排序、HTML 原文、附件哈希归一化和 topicId 归属修正时不得自行改变序列化规则。

## 5. Topic 配置版本契约

Agent Topic 的线上字段为：`id`、`name`、`createdAt`、`locked`、`unread`、`ownerId`、`configHash`、`updatedAt`。Group Topic 不含 `locked` 与 `unread`，其余配置版本字段相同。

`configHash` 与 `updatedAt` 都是必填项：

- `configHash` 是 Topic 配置字段的 SHA-256，不代表消息集合。
- `updatedAt` 是该配置版本的仲裁时间。
- pull/upsert 必须把远端两项原样写入数据库，不能按接收时刻重算或覆盖。
- 新建本地 Topic 时必须立即根据实际配置生成 `configHash`，并持久化 Agent Topic 的 `locked/unread`。
- 消息增加、修改或删除只刷新 Topic `content_hash` 并向 Owner 冒泡；不得改写 `config_hash` 或配置 `updated_at`。

这条边界保证“改消息”和“改话题配置”是两个独立版本域，避免内容同步伪装成配置更新并错误赢得 LWW 仲裁。

## 6. 错误与诊断

Wire 错误对象固定为七个 camelCase 字段：`code`、`origin`、`stage`、`kind`、`retry`、`message`、`failedTopicIds`。未知字段、开放枚举值、过长消息或 topic ID、无效 code 都会被拒绝或有界化处理。

迁移排障时优先关注：

| 错误码 | 含义 | 恢复动作 |
|--------|------|----------|
| `WIRE_VERSION_MISMATCH` | 手机与桌面的 Wire claim 不一致 | 更新两端；不要通过修改插件包版本绕过 |
| `VERSION_ACK_INVALID` | ACK 结构、声明集合或后端模式非法 | 核对握手 fixture 与桌面插件 |
| `CDS_BINARY_NOT_FOUND` | 桌面 CDS 运行文件缺失 | 在 VCPChat 根目录编译 CDS 并重启桌面端 |
| `CDS_PROTOCOL_MISMATCH` | 插件与 CDS 内部协议不一致 | 更新桌面代码、重新编译 CDS 并重启 |
| `FINAL_ACK_INVALID` | 最终 ACK 身份或字段集合不匹配 | 排查迟到帧、重复帧或旧桌面实现 |
| `FINAL_ACK_TIMEOUT` | 最终确认未在期限内到达 | 保留诊断并检查桌面日志/连接 |

同步页展示桌面后端与插件包版本，并保留“复制诊断”。对于需要重建 CDS 的错误，还会显示并复制：

```text
node rust_chat_data_service/build-runtime.js
```

诊断文本会清理 token 和本地路径；不得把真实凭据、消息正文或个人数据加入错误 payload。

## 7. 从 Wire 1.4 迁移

本次迁移是硬切换，不是双栈：

1. 桌面端升级到 `VCPMobileSync 2.0.0 / Wire 1.5`，并确保 CDS 与插件来自同一代码版本。
2. 移动端升级后重新建立同步连接；旧式 `mobileVersion` / `version` 扁平握手会被拒绝。
3. 不修改或重跑数据库迁移 `wire-1.4-message-v1`。该名称记录的是既有消息 fingerprint 数据迁移，不等同于运行时仍支持 Wire 1.4。
4. `sync_hash_initializer/wire14.rs`、Android E2E 的 `wire14` 目录和合成数据前缀作为历史稳定标识保留，不代表双栈能力。
5. 若出现兼容错误，先核对 Wire claim，再核对 CDS 构建；插件包版本只用于判断桌面安装来源，不作为放行条件。

## 8. 修改协议时的门禁

任何触及握手、ACK、Message/Topic DTO 或错误表的改动，至少需要同时满足：

- 五份 fixture 与当前桌面插件字节一致。
- Rust 的 fixture、严格 JSON、握手、DTO、push/pull、持久化、hash 和并发状态机测试通过。
- 前端同步会话测试覆盖桌面信息生命周期、陈旧事件隔离、错误文案和诊断复制。
- Android E2E 离线 gate 通过；真实设备验收仍以项目 harness 的 hard-gate 结果为准。
- 全量 Rust 测试、前端测试、构建、格式化与 `git diff --check` 通过。
